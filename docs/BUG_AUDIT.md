## 1. AI-1 — Fault Classifier (Training & Data)

This is the weakest area in the project. The model is trained on a dataset whose
labels are largely an artefact of the data's shape rather than real fault physics.

### 1.1 — CRITICAL · Sequences are built from *shuffled* rows

`build_dataloaders()` calls `train_test_split(..., shuffle=True)` (the default) and
**then** feeds the shuffled array into `OrbitalSequenceDataset`, which slices
consecutive rows into 8-step windows:

```python
X_tv, X_test, y_tv, y_test = train_test_split(X_scaled, y_raw, ...)   # shuffles
train_ds = OrbitalSequenceDataset(X_train, y_train, seq)              # windows the shuffle
```

Every "temporal sequence" is therefore 8 **unrelated satellites** stitched together.
The Transformer's positional encoding and self-attention have nothing real to learn;
because the label is taken from the last row (`y[i + seq_len - 1]`), the model
collapses to single-row classification with 7 rows of noise prepended.

**Knock-on effect:** at inference the pipeline feeds a *coherent* 8-epoch window of a
single satellite — completely out of distribution relative to training.

**Fix:** group by `NORAD_CAT_ID`, sort by `EPOCH`, build windows *within* each
satellite, and split by satellite (`GroupShuffleSplit`) so no satellite appears in
both train and test.

### 1.2 — CRITICAL · Windows span satellite boundaries

Even with shuffling removed, `OrbitalSequenceDataset` slides over the whole array
without grouping. Windows straddle the boundary between one satellite and the next.

### 1.3 — CRITICAL · The dataset has no time dimension, so 3 of 4 fault rules cannot fire **[verified]**

> **Data provenance.** These CSVs are a partly-synthesised snapshot: genuine CelesTrak
> GP elements with the unavailable/restricted fields stubbed out (`ELEMENT_SET_NO = 999`
> on every row, `EPHEMERIS_TYPE = 0`, `MEAN_MOTION_DDOT` nonzero in only 27/854). That
> is a reasonable response to real fault-labelled telemetry being restricted — this
> finding is **not** a criticism of using synthetic data. It is about the *shape* of
> what was generated.

The dataset is a single instant in time: 854 rows, 712 unique satellites, and **no
satellite has two distinct epochs**. The 251 repeated rows are 141 *exact* duplicates
caused by the three CSVs overlapping (CubeSats and amateur satellites also appear in
the general catalog):

```
REV_AT_EPOCH changes across epochs : 0 satellites
REV_AT_EPOCH identical             : 109 satellites
duplicate (NORAD_CAT_ID, EPOCH) pairs : 141

CUTE-1 (CO-55)  2026-06-10 07:02:25.997280+00:00  14.243315  0.000906  19069.0
CUTE-1 (CO-55)  2026-06-10 07:02:25.997280+00:00  14.243315  0.000906  19069.0
CUTE-1 (CO-55)  2026-06-10 07:02:25.997280+00:00  14.243315  0.000906  19069.0
```

Three of the four fault signatures are defined as **changes between consecutive
epochs**, computed with `groupby(...).diff().fillna(0)`. With one epoch per satellite,
every difference is zero:

```
REV_DELTA == 0 for : 100.0 % of rows
ecc_delta == 0 for : 100.0 % of rows

Resulting label distribution:
  SOFTWARE_BUG           807     <-- catch-all: rev_delta <= 0 matches everything
  FIRMWARE_CORRUPTION     23     <-- absolute thresholds, so these still work
  COMMAND_INJECTION        9
  SEU                      0     <-- rule can never fire
  NORMAL                   0
```

Only the two rules based on *absolute* thresholds (`BSTAR`, `MEAN_MOTION_DOT`) survive.
`if rev_delta <= 0: return "SOFTWARE_BUG"` then absorbs 95% of the dataset, and the SEU
class ends up 100% synthetic — generated by `_generate_synthetic_class`, which defines
SEU differently (§1.4).

**This is also the root cause of §1.1/§1.2.** A `seq_len=8` Transformer with positional
encoding is modelling a time axis the data does not have, which is why the windowing
code could be shuffled without anyone noticing.

**Fix — and it is entirely within your control, since the data is synthesised.**
Generate multi-epoch series per satellite instead of a one-instant snapshot. Everything
needed is already in the repo: `sgp4` is a dependency, and
`satellite_catalog.build_tle_from_gp()` already converts a GP row into a valid TLE. For
each satellite, propagate its elements forward over N epochs (say 20 epochs at ~90-minute
intervals), re-deriving the osculating elements at each step, then inject faults as
*perturbations to the series*:

| Fault | Injection into the propagated series |
|---|---|
| SEU | one-epoch step in `ECCENTRICITY`/`MEAN_ANOMALY`, reverting next epoch |
| SOFTWARE_BUG | freeze or roll back `REV_AT_EPOCH` for a run of epochs |
| FIRMWARE_CORRUPTION | ramp `BSTAR`/`MEAN_MOTION_DOT` beyond threshold |
| COMMAND_INJECTION | stop emitting epochs, so `TLE_AGE_HOURS` grows past 72 |

That single change makes `REV_DELTA` and `ecc_delta` meaningful, gives SEU real
examples, gives the Transformer genuine dynamics to attend over, and removes the need
for `_generate_synthetic_class` entirely.

Also dedup the three CSVs on `(NORAD_CAT_ID, EPOCH)` at load time — `clean_orbital_data`
does this, but `satellite_catalog.load()` silently keeps whichever row came first (§5.6).

### 1.4 — CRITICAL · Synthetic SEU contradicts the SEU label rule

`assign_fault_labels()` defines SEU as a *jump* in eccentricity between epochs.
`_generate_synthetic_class("SEU", ...)` defines it as a *constant* `ECCENTRICITY=0.05`.
Since all SEU training data is synthetic (1.3), the model actually learns
"SEU = eccentricity near 0.05" — a different concept from the documented one, and one
no real satellite window will reproduce.

### 1.5 — CRITICAL · Augmentation before split ⇒ train/test leakage

`augment_fault_samples()` oversamples **with replacement** and adds noise of only
`0.05 × class_std`, producing near-duplicates. This happens *before*
`build_dataloaders()` splits. FIRMWARE_CORRUPTION has 23 real rows expanded to 400, so
the same 23 rows appear — barely perturbed — in train, val and test.
**Reported test accuracy is meaningless.**

### 1.6 — HIGH · Scaler fitted on the full dataset ⇒ leakage

`train_isolation_forest(df_clean)` fits the `StandardScaler` on **all** rows and
returns it; `build_dataloaders()` then calls `scaler.transform()` on the split data.
Test-set statistics leak into the training normalisation. The scaler is also fitted on
`df_clean` (pre-augmentation, includes NORMAL) but applied to `df_faults` — a
distribution mismatch on top of the leak.

### 1.7 — HIGH · No "healthy" output class

`FAULT_LABELS` has exactly 4 entries and `augment_fault_samples()` drops every NORMAL
row (`df["fault_label"] != "NORMAL"`). The classifier **cannot output "nominal"** — a
perfectly healthy satellite is always assigned one of four faults. For a system whose
purpose is deciding whether to uplink recovery commands, this is a serious design gap.

### 1.8 — HIGH · The Isolation Forest gate gates nothing

`predict()` returns `anomaly_flag` alongside `fault_class`, but the two are computed
independently and no caller uses `anomaly_flag` to suppress a classification. The
"anomaly gate" in the architecture diagram does not exist in code.

### 1.9 — MEDIUM · Isolation Forest trained on faulty data, reported metric is circular

`iforest.fit(X_scaled)` uses all rows including faults, so faults are learned as
normal. The printed `anomaly_pct` is then measured on the same data it was fitted to —
with `contamination=0.05` it is ~5% **by construction**, not a finding.

### 1.10 — MEDIUM · Class balance never actually achieved

`n_needed = max(0, target_per_class - len(class_df))` returns 0 for SOFTWARE_BUG (807 >
400), so it is left at 807 while the others are padded to 400. Final ratio ≈ 2:1:1:1
despite the function's stated purpose.

### 1.11 — MEDIUM · Augmentation ignores the seeded RNG

`np.random.normal(0, std, n_needed)` uses the global NumPy RNG while the surrounding
code uses `random_state=CONFIG["random_seed"]`. Training runs are not reproducible.

### 1.12 — MEDIUM · `_generate_synthetic_class` reseeds identically per class

`rng = np.random.default_rng(CONFIG["random_seed"])` is re-created inside every call,
so all four synthetic classes draw the *same* noise sequence — correlated noise across
classes.

### 1.13 — LOW · V1 and V2 classifiers coexist with incompatible contracts

`satellite_fault_classifier.py` (V1) uses `TELEMETRY_COLS` and has no `FEATURE_COLS`;
V2 uses 11 orbital elements. Both ship, both are imported in different places, and
nothing marks V1 as deprecated.

### 1.14 — LOW · `MEAN_MOTION_DDOT` is always zero in the source data

It is in `FEATURE_COLS` but every CSV row has `0`. A constant feature contributes
nothing and slightly dilutes the attention input.

## 2. AI-1 → AI-2 Integration

### 2.1 — CRITICAL · Fault-key case mismatch ✅ **FIXED**

Classifier emitted `SOFTWARE_BUG`; `procedure_library.json` is keyed `software_bug`;
`node_select_procedure` does a direct dict lookup. Unnormalised, recovery fails.
Fixed by `models/classifier_inference.py` (`FAULT_KEY_MAP` / `normalise_fault_key`).

### 2.2 — HIGH · Whole pipeline hard-imported torch ✅ **FIXED**

`CONFIG`/`FEATURE_COLS` lived inside the 887-line training module, so even pure-logic
key normalisation was unimportable without torch. Extracted to
`models/feature_spec.py`; V2 re-exports it.

### 2.3 — MEDIUM · Emulator naming asymmetry ✅ **FIXED**

`inject_command()` vs the `command_injection` library key; no `norad_id` on the
emulator. Added `inject_command_injection()` alias and a `norad_id` constructor arg.

### 2.4 — HIGH · No model-versioning check on artifacts

`meta.json` stores `feature_cols`, and the bridge warns on mismatch, but nothing
records the training-data hash, git SHA or a model version. Silently loading artifacts
trained on a different label scheme will produce confident wrong answers.

## 3. AI-2 — Recovery Agent

### 3.1 — CRITICAL · Success is declared on `health == "nominal"`, bypassing criteria

```python
if passed or health == "nominal":
    state["recovery_success"] = True
```

`success_criteria` are advisory. Because `apply_recovery()` resets subsystem statuses
(§4.1), health flips to nominal immediately and recovery is declared successful on the
first poll. **The verification step is effectively a no-op**, and the fallback path is
almost unreachable — which means the headline "automatically falls back to an alternate
procedure" claim is untested in practice.

### 3.2 — CRITICAL · Signature failure is silently converted into success

```python
except Exception as sign_err:
    print(f"[Agent]    CY-1 unavailable ({sign_err}), using MOCK signing")
    signed.append({**cmd, "signed": True, "signature": f"MOCK_SIG_..."})
...
state["signing_success"] = True
print("[Agent]    CY-1 signing SUCCESS")
```

Any failure — service down, network error, HTTP 500, malformed response — produces a
fake signature that is marked `signed: True`, after which the agent prints
"signing SUCCESS". **Taking the crypto service offline bypasses command signing
entirely.** This also makes `route_after_signing`'s `"fallback"` branch dead code.

### 3.3 — CRITICAL · Signed commands are never verified before execution **[verified]**

`verify_command()` is called only from inside `crypto/` (the `/crypto/verify` endpoint
and a startup self-test). Nothing in the recovery path verifies anything:

```
$ grep -rn "verify_command" --include=*.py . | grep -v crypto/
(no results)
```

`node_uplink_commands` calls `emulator.apply_recovery(proc_name)` directly, and the
emulator has no signature check. The entire crypto layer is decorative in the flow it
exists to protect.

### 3.4 — CRITICAL · `min_confidence` skip corrupts agent state

On a confidence skip, `node_select_procedure` increments `priority_index` and returns
**without** setting `selected_procedure`, `error` or `next_step`. The inline comment
says "graph will re-enter select", but no such edge exists. `route_after_select` sees
no error and routes to `generate_commands`, which reads `state["selected_procedure"]` —
either unset (KeyError, swallowed into `state["error"]`) or **stale from a previous
iteration**, silently generating and uplinking commands for the wrong procedure.

**Live trigger:** `software_bug` has `min_confidence` 0.70 (primary) then 0.80
(fallback). Any confidence in **[0.70, 0.80)** hits this path.

### 3.5 — HIGH · Uplink is always allowed regardless of ground contact

`node_schedule_uplink` sets `state["uplink_allowed"] = True` in the in-contact branch,
the no-contact branch (`# dev mode`), *and* the exception handler. Contact-window
scheduling has no effect on behaviour. A hardcoded dev-mode override should not ship in
the path the README describes as "schedules the uplink for the next ground-contact
window".

### 3.6 — HIGH · `apply_recovery()`'s return value is discarded

```python
success = emulator.apply_recovery(proc_name)   # never read again
```

If the emulator rejects the procedure (unknown name → `False`), the agent proceeds to
monitoring as though the uplink succeeded.

### 3.7 — HIGH · `_check_criteria` treats a missing key as PASS

```python
val = frame.get(key)
if val is None:
    continue          # missing telemetry == criterion satisfied
```

A typo or renamed field silently disables that check. **Live instance:**
`SAFE_MODE_HOLD` requires `beacon_active`, which the emulator never emits **[verified]** —
so that criterion is always skipped.

### 3.8 — HIGH · `>=` and `<=` operators silently always fail

`condition.startswith("<")` then `float(condition[1:])`. For `"<= 0.01"` the slice is
`"= 0.01"`, `float()` raises `ValueError`, and the handler falls through to a string
comparison that returns `False`. The library happens to use only `<`/`>` today, so this
is latent — but it fails closed-then-open in a confusing way.

### 3.9 — HIGH · JSON boolean criteria raise an uncaught `AttributeError`

If any `success_criteria` value is a JSON boolean, `condition.startswith(...)` raises
`AttributeError`, which is **not** in the `except (ValueError, TypeError)` clause. The
node crashes. Currently no boolean criteria exist, so this is latent.

### 3.10 — MEDIUM · Attempt counter conflates skips with attempts

`attempt_count` is incremented both by `node_fallback` and by a `min_confidence` skip,
while `route_after_fallback` compares it against `priority_list_len`. A single
confidence skip can therefore exhaust the budget before every procedure has been tried.

### 3.11 — MEDIUM · `timeout_s` is interpreted as a poll count and silently capped

`max_a = min(int(timeout), MAX_POLL_ATTEMPTS)` with `POLL_INTERVAL_S = 1.0`. A
procedure declaring `timeout_s: 90` gets 30 polls ≈ 30 s. The units only coincide
because the interval is 1 s.

### 3.12 — MEDIUM · A new `ContactCalculator` is built per attempt

`node_schedule_uplink` constructs one and calls `load_tle()` every time, triggering a
fresh blocking CelesTrak fetch (5 s timeout) on each fallback. No caching.

### 3.13 — MEDIUM · `LOG_DIR.mkdir()` runs at import time

Module-level side effect, and without `parents=True` it raises if the parent is
missing. Importing the agent should not touch the filesystem.

### 3.14 — MEDIUM · Recovery-log filenames collide

`strftime("%Y%m%d_%H%M%S")` — two runs in the same second overwrite each other, which
`pipeline.py --all` can hit.

### 3.15 — MEDIUM · Endpoints hardcoded to `localhost:8000`

`SIGNING_ENDPOINT` and `FASTAPI_BASE` are constants with no environment override, so
the agent cannot run on a different host or port from the API. `satellite_id` is
likewise hardcoded to `"DEADSAT-1"` while `norad_id` is parameterised.

### 3.16 — LOW · `if bat_cur and alt:` drops the note at 0% battery

A `battery_pct` of `0` is falsy, so the baseline reasoning note is suppressed exactly
when the satellite is in its worst state.

### 3.17 — LOW · `_find_procedure_library()` returns a non-existent path

If no candidate exists it returns `candidates[0]` anyway, converting a clear
"file not found" into a later confusing open error.

### 3.18 — LOW · Redundant re-import inside a function

`from datetime import datetime, timezone` inside `node_schedule_uplink`, already
imported at module scope.

### 3.19 — LOW · Smoke test leaks a thread

The `__main__` block starts an emulator and never calls `stop()`.

## 4. Satellite Emulator

### 4.1 — CRITICAL · Any recognised procedure "cures" any fault **[verified]**

`apply_recovery()` ends with an unconditional
`self.fault_injected = FaultType.NONE` and prints
`"Recovery SUCCESS — satellite nominal"` for **any** name it recognises, regardless of
whether it addresses the active fault:

```
after SEU        : health= fault  adcs= fault
apply_recovery("LOCKDOWN_REGEN_v1")   <-- comms procedure, wrong for an SEU
after WRONG proc : returned True | health= fault | adcs= fault | fault_injected= none
```

The fault flag is cleared (so symptoms stop progressing) and the log claims success,
while ADCS is still in `fault`. This is what makes §3.1 so damaging: the emulator's
notion of "recovered" is decoupled from the fault it was recovering from.

### 4.2 — HIGH · `start()` is not idempotent — orphaned duplicate threads **[verified]**

```
thread after 1st start: Thread-2 (_tick_loop) alive= True
thread after 2nd start: Thread-3 (_tick_loop) alive= True
ORPHANED duplicate ticking: True
```

`self._thread` is overwritten, so the first thread keeps ticking (it only observes
`_running`) and is never joined. Two threads then mutate subsystem state at different
phases. Reachable via `main.py` lifespan plus any code path that calls `start()` again.

### 4.3 — HIGH · Unclamped power drift breaks a success criterion **[verified]**

`power.solar_output_w`, `bus_voltage_v` and `reaction_wheel_rpm` are random walks with
no bounds (unlike `battery_pct`, which is clamped):

```
power_w after ~2000 nominal ticks : 46.64   (criterion requires power_w > 75)
```

At the API's `tick_interval=1.0`, that is ~33 minutes of uptime — after which
`command_injection` recovery verification fails spuriously. A long-running demo will
break on its own.

### 4.4 — HIGH · Fault effects escalate without bound **[verified]**

`_apply_fault_effects()` adds to the same fields every tick with no ceiling:

```
adcs_rate_deg_s after ~150 ticks : 14.68   (nominal < 0.01)
obc_error_count                  : 147
```

A reaction wheel cannot slew a spacecraft at 14.7 °/s indefinitely; the telemetry
becomes physically meaningless the longer a fault is left uncorrected.

### 4.5 — MEDIUM · Documented "noise during faults" does not exist **[verified]**

`recovery_agent.py`'s header claims *"Improvement 2 — Fault state telemetry has noise
on top of fault effects"*. In fact `_update_nominal_drift()` returns early unless
`fault_injected in (None, FaultType.NONE)`:

```
distinct obc_temp_c values during fault: 1 -> FROZEN
```

Unaffected subsystems freeze completely during a fault, which is both unrealistic and a
trivial giveaway to any downstream detector.

### 4.6 — MEDIUM · `get_latest_frame()` is only a shallow copy

`dict(self._latest_frame)` shares the nested `fault_detail` dict by reference. A caller
mutating it corrupts emulator state. `main.py` already mutates the returned frame
(`frame["overall_health"] = ...`) — safe today only because it is a top-level key.

### 4.7 — MEDIUM · `stop()` can leave the thread running

`join(timeout=3)` with no post-check. If `tick_interval > 3`, the thread is still
sleeping when `stop()` returns and no warning is raised.

### 4.8 — LOW · Startup message is hardcoded and wrong

`print("[Emulator] Started — streaming telemetry every 1s")` regardless of the actual
`tick_interval` (the pipeline uses 0.3 s, tests use 0.05 s).

## 5. Orbital Mechanics — Contact Calculator & Catalog

### 5.1 — HIGH · Fallback TLE is two years stale

```python
"line1": "1 28654U 05018A   24163.50000000  ..."
```

Epoch `24163` = day 163 of **2024**. The project's own timeline is 2026. LEO TLEs
degrade within days to weeks; propagating one two years forward yields positions wrong
by thousands of kilometres, so every offline contact window is fiction.
`recovery_agent.py` nonetheless claims *"Improvement 4 — Fallback TLE updated to recent
epoch"*.

### 5.2 — HIGH · `find_next_contact` blocks for thousands of propagations

The agent calls it with `search_hours=24.0, step_seconds=10.0` → **8,640** SGP4
propagations plus trig, synchronously, inside the recovery graph. The comment labels
this "Bug Fix 4: step_seconds=10 for accurate AOS timing" — which tripled the cost
versus the 30 s default. A coarse scan followed by refinement near the crossing would
be ~50× cheaper.

### 5.3 — HIGH · `/contact` runs three full propagation passes

`get_contact_summary()` calls `get_current_azel()`, `find_next_contact()` **and**
`is_in_contact_now()` (which internally calls `get_current_azel()` again). Three scans
where one would do.

### 5.4 — MEDIUM · `load_tle()`'s failure return is ignored everywhere

It returns `False` when sgp4 is missing, but `node_schedule_uplink` ignores the result
and proceeds; `self.sat` stays `None`, every query returns `None`/`False`, and dev-mode
(§3.5) allows the uplink regardless. Failure is indistinguishable from "no window".

### 5.5 — MEDIUM · Fetched TLE is never validated

`lines[1]` and `lines[2]` are used with no check that they begin with `1 `/`2 `, are 69
characters, or have valid checksums. A CelesTrak error page produces garbage that
`Satrec.twoline2rv` may accept or reject unpredictably. `fetch_tle` has a `try/except`
but `load_tle`'s `twoline2rv` call does not.

### 5.6 — MEDIUM · Catalog keeps the *first* row per NORAD, not the newest

```python
if nid not in seen:
    seen.add(nid); self._catalog[nid] = row
```

854 rows collapse to 712 satellites, so 142 rows are discarded by **file order**, not
by epoch. For the 109 satellites with multiple epochs, the catalog may serve a stale
element set. Should sort by `EPOCH` and keep the latest.

### 5.7 — MEDIUM · Ground-station altitude units are ambiguous

`GROUND_STATION["alt_m"] = 53.0` (metres) is passed to a parameter documented as
`gs_alt: km`, and the body computes `R_E + gs_alt / 1000.0`. The arithmetic is correct
for metres, so the *docstring* is wrong — but any caller trusting the docstring
introduces a 1000× error.

### 5.8 — LOW · Reports the current pass as the "next" contact

If the satellite is already above the horizon at `t = now`, the scan latches AOS at
`now`, so `find_next_contact()` returns the in-progress pass.

### 5.9 — LOW · `get_by_name()` returns the first substring match

`"NOAA"` matches whichever NOAA satellite appears first in file order, with no
disambiguation or warning.

## 6. FastAPI Backend & WebSockets

### 6.1 — CRITICAL · No authentication on any endpoint, with wildcard CORS

```python
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], ...)
```

Combined with unauthenticated mutating routes — `/fault/inject`, `/recovery/trigger`,
`/pipeline/run`, `/reset`, `/seed`, `/crypto/sign` — **any web page the operator visits
can inject faults into and command the ground station.** For a project whose thesis is
authenticated satellite command, this undercuts the entire premise.

### 6.2 — HIGH · Module-level emulator breaks multi-worker deployment

`emulator = SatelliteEmulator(tick_interval=1.0)` is instantiated at import. Under
`uvicorn --workers N` each worker gets its own emulator with independent state, so
polling clients see randomly different telemetry. `--reload` produces the same problem.

### 6.3 — HIGH · A single WebSocket error kills telemetry for everyone

```python
async def _telemetry_broadcaster():
    while True:
        await asyncio.sleep(1.0)
        ...
        await ws_manager.broadcast_telemetry(frame)
```

No `try/except` inside the loop. One raised exception ends the task permanently and all
clients silently stop receiving telemetry until the process restarts. There is also no
`asyncio.CancelledError` handling for clean shutdown.

### 6.4 — MEDIUM · Executor is replaced but never shut down

`loop.set_default_executor(ThreadPoolExecutor(max_workers=10))` — the previous executor
is discarded and the new one is never `shutdown()`, leaving threads on exit.

### 6.5 — MEDIUM · `asyncio.get_event_loop()` inside a running loop

Deprecated since 3.10 and slated for removal; should be `get_running_loop()`. Appears in
the lifespan and in `/contact`.

### 6.6 — MEDIUM · `/telemetry` can return an almost-empty frame

Before the first tick, `get_latest_frame()` returns `{}`, so the endpoint responds with
only `overall_health`. No readiness gate.

### 6.7 — MEDIUM · Fire-and-forget tasks are never tracked

`/recovery/trigger` and `/pipeline/run` both call `asyncio.create_task(...)` without
retaining a reference. The task can be garbage-collected mid-flight, and nothing
prevents two concurrent recoveries racing on the same emulator.

### 6.8 — MEDIUM · `backend/` is a divergent second copy of the whole application

`backend/main.py` differs from `main.py` by ~250 lines (crypto routes, different
`sys.path` setup), and `backend/pipeline/` mirrors `models/` under another name. Two
copies of the emulator, catalog, agent and classifier must be kept in sync by hand —
they had already drifted before this audit. Pick one tree.

### 6.9 — LOW · No rate limiting on fault injection

`/fault/inject` can be called in a tight loop, compounding §4.4's unbounded escalation.

## 7. Cryptography & Security

### 7.1 — CRITICAL · The verification path is never exercised by the system

See §3.3. `verify_command()` exists, is well written, and is unreachable from the
recovery flow.

### 7.2 — CRITICAL · Nonce replay check is a TOCTOU race

```python
# comment claims: SET NX — atomic, only sets if key doesn't exist
existing = self.redis.get(key)     # <-- separate read
if existing is not None: ...
self.redis.set(key, nonce, ...)    # <-- separate write
```

The code does **not** use `nx=True` despite the comment. Two concurrent requests with
the same nonce both observe `None` and both proceed. The `threading.Lock` only
serialises within one process — with multiple uvicorn workers (§6.2) it provides no
protection at all.

### 7.3 — HIGH · A failed nonce comparison silently *overwrites* the nonce

If `hmac.compare_digest(nonce_bytes, existing.encode())` returns `False`, control falls
through to the unconditional `redis.set(...)`, replacing the stored nonce and allowing
the replay it was meant to block.

### 7.4 — HIGH · Nonce is consumed at signing time, not at verification time

`crypto_routes.sign()` calls `_nonce_manager.use_nonce(...)`; the `/verify` endpoint
never checks it. Replay protection is therefore applied to the party issuing
signatures rather than the party accepting them — the wrong side of the trust boundary.

### 7.5 — HIGH · `sys.exit(1)` inside a library function

```python
except oqs.MechanismNotSupportedError:
    print(f"[FAIL] {ALGORITHM} not supported — check liboqs build")
    sys.exit(1)
```

A verification helper terminates the entire FastAPI process on an unsupported
mechanism. It should raise.

### 7.6 — MEDIUM · Documented timing-attack protection is not implemented

`verify.py` states *"Uses hmac.compare_digest() to prevent timing attacks"* and carries
the comment `# hmac.compare_digest — timing-attack resistant final check` immediately
after `ed25519_ok = True`. `compare_digest` is never called; `import hmac` is unused.
The claim is false. (PyNaCl's own `verify()` is constant-time, so the underlying check
is fine — the documentation is what is wrong.)

### 7.7 — MEDIUM · Hard dependency on Redis with no degradation path

`NonceManager.__init__` re-raises on `redis.ConnectionError`, so the crypto routes
cannot start without Redis — even though a `mock_oqs_nacl.py` fallback exists for the
much heavier liboqs dependency.

### 7.8 — MEDIUM · `import oqs` at module scope in `crypto/verify.py`

No `try/except`, so the root tree hard-fails without liboqs while `backend/crypto/`
ships `mock_oqs_nacl.py`. The two trees have different failure behaviour.

### 7.9 — MEDIUM · 120-second TTL versus a 24-hour contact wait

`TTL_SECONDS = 120`, but the agent may schedule an uplink for the next contact window
up to 24 hours out. Any command actually held for a real window expires before
transmission. The two subsystems' time horizons were never reconciled.

### 7.10 — LOW · Private keys are memory-only with no rotation story

`keygen.py` persists only public keys and prints `Private keys saved : NO (memory
only)`. Every restart invalidates previously issued signatures, and the ledger's
historical entries become unverifiable.

## 8. Frontend

### 8.1 — CRITICAL · The frontend is not connected to the backend at all **[verified]**

Across every `.tsx`/`.ts` file there are exactly **two** network-related references:

```
components/SatelliteDashboard.tsx:248  fetch('https://celestrak.org/...CATNR=44804...')
components/SatelliteDashboard.tsx:317  `[...] WebSocket client OP-HQ_DELHI handshaking...`
```

The second is a **hardcoded log string**, not a WebSocket. There is no call to
`/telemetry`, `/ws/telemetry`, `/fault/inject`, `/recovery/trigger` or any other
endpoint. All dashboard telemetry is generated client-side:

```js
powerArray: prev.powerArray + (Math.random() - 0.5) * 0.3
obcCpu:     prev.obcCpu + Math.floor((Math.random() - 0.5) * 4)
```

The React app is a self-contained simulation. The entire Python backend — emulator,
classifier, agent, crypto — is unreachable from the UI, so the "Live System Proof"
screenshots demonstrate `Math.random()`, not the recovery pipeline.

### 8.2 — HIGH · Browser-side CelesTrak fetch will be blocked by CORS

`fetch('https://celestrak.org/NORAD/elements/gp.php?...')` from the page origin.
CelesTrak does not send `Access-Control-Allow-Origin` for this endpoint, so the call
fails in a browser. It also hardcodes **NORAD 44804**, unrelated to the project's
28654/NOAA-18.

### 8.3 — MEDIUM · No API base URL configuration

There is no `VITE_API_BASE` (or equivalent) anywhere, so even once wiring is added
there is no way to point the build at a backend host.

### 8.4 — MEDIUM · `.env.example` requests a key nothing consumes

`GEMINI_API_KEY` is documented, `@google/genai` is a dependency, and neither appears in
any source file. Asking users to supply an unused API key is a needless secret-handling
risk.

### 8.5 — LOW · `express` is a runtime dependency of a static SPA

Listed under `dependencies` (not `devDependencies`) with no server code; the `clean`
script deletes a `server.js` that does not exist.

### 8.6 — LOW · Package is still named `react-example`

Scaffold leftover in `package.json`.

### 8.7 — LOW · Mojibake in `vite.config.ts`

`// Do not modifyâfile watching is disabled` — a UTF-8 em-dash mis-decoded as
Latin-1.

## 9. Repository Hygiene & Build

### 9.1 — HIGH · Mixed CRLF/LF line endings with no `.gitattributes`

~50 files show as modified on checkout purely from line-ending differences
(`git diff --ignore-cr-at-eol` on them is empty). This buries real changes in review
noise. Add a `.gitattributes` with `* text=auto`.

### 9.2 — MEDIUM · `.gitignore` misses generated artefacts

Not ignored: `model_artifacts/`, `recovery_logs/`, `crypto/nonce_store.db`,
`crypto/*.bin`, `node_modules/`. Two `recovery_logs/*.json` run outputs are already
committed.

### 9.3 — MEDIUM · Binary blobs committed to the repo

`PCB&&CAD.zip` (68 KB) and `docs/For a satellite fault.docx` (18 KB). The `&&` in the
filename also breaks naive shell globbing.

### 9.4 — MEDIUM · Dependency pinning is inconsistent

`langgraph==1.2.4` and `langchain-core==1.4.2` are exact-pinned while everything else
is `>=`-floored with no upper bound. There is no lockfile, so Python builds are not
reproducible.

### 9.5 — LOW · Duplicated data files

`data/` and `backend/data/` hold identical CSVs (~1.3 MB duplicated), alongside the
whole-tree duplication in §6.8.

### 9.6 — LOW · No CI

No workflow runs `test_integration.py`, so none of the above regresses visibly.
